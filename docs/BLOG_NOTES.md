## Working thesis: testability makes the product better

The line-and-column indicator is a small but unusually clear example.

During the testing work, the model added a top-bar indicator showing the live
cursor position—`Ln x, Col y`. The likely immediate motivation was
observability: cursor position is important to the editing model and easier to
test when the interface exposes it clearly. Verify that motivation from the
implementing conversation or commit before stating it as fact.

Whatever the original motivation, the result is not merely test scaffolding.
It is a genuinely useful editor feature. While dogfooding Quillex, the
indicator immediately felt like something worth keeping.

This supports a broader point:

> Making behavior observable enough to test often makes the software more
> understandable and humane for the person using it.

Testing and usability are sometimes described as competing concerns—internal
machinery versus visible polish—but good observability can serve both. The
test wants an unambiguous answer to “where is the cursor?” The user benefits
from exactly the same answer.

### Narrative claim to develop

The inflection was not simply “AI wrote more code.” Claude Code made a new
development loop feel viable: agents could operate the application, generate
Scenic integration scenarios, inspect rendered/semantic state, and use Spex to
turn visual behavior into repeatable evidence. Once the editor could be tested
through something resembling user interaction, development became cumulative
in a different way.

This claim should combine three kinds of evidence:

1. **Firsthand account:** what changed in the author's daily process when
   Claude Code appeared.
2. **Repository archaeology:** the dated commits above, growth of `test/spex`,
   ScriptInspector/semantic tooling, and later architecture changes motivated
   by failures those tests exposed.
3. **Honest critique:** generated tests also became flaky, privileged Boundary
   exports could let agents cheat, and large quantities of test code did not
   guarantee trustworthy evidence. The method improved by auditing its own
   test machinery.

Avoid a simplistic before/after productivity graph. The more interesting
story is a change in epistemology: before, progress often meant “it appears to
work”; afterward, the project increasingly tried to encode what “works” meant
for a real Scenic window—even when the first versions of that evidence were
messy.

There is a second architectural layer to the example. `CursorPosLabel` is a
small independent Scenic component that subscribes directly to the stable pane
source. RootScene does not need to receive every keystroke or manually update
the label. The feature therefore demonstrates the store architecture in
miniature:

```text
Buffer.Process snapshot
        ↓
PaneStore stable source
        ├── TextField renders the document
        └── CursorPosLabel renders Ln x, Col y
```

One observable fact supports two consumers without coupling them to one
another. Testability, user feedback, and architecture line up.

### Useful tension to retain in the post

The audit also found that the indicator currently receives a fixed 110 px of
top-bar space. Large line/column values may require more room and compete with
the tab bar. That is a nice honest continuation of the story: a testing-driven
feature can improve the product and still need ordinary product-design work.

## Boundary: making the test architecture enforceable

Quillex uses the Elixir [`boundary`](https://hex.pm/packages/boundary) library
to turn architectural intent into compile-time dependency checks. The key
point for the post is not merely “we use a library”; it is that the test
harness has an architecture too.

Current boundaries include:

- `Quillex` as the application boundary, with an explicit export surface;
- `Quillex.TestHelpers`, which exports the approved viewport, semantic,
  invariant, performance, and model-oracle helpers;
- `Quillex.Spex`, which may depend on the test-helper boundary, Scenic MCP,
  and the Spex framework;
- `Quillex.Mix`, which isolates custom Mix tasks from runtime application
  code.

This makes an important distinction visible: tests are allowed to observe the
application through deliberately designed interfaces, but should not acquire
arbitrary knowledge of every internal module merely because they live in the
same repository. Where a model oracle or deterministic test control needs
deeper access, that access becomes an explicit export and therefore an
architectural decision rather than an accidental shortcut.

Possible phrasing:

> A test suite can violate the design just as easily as production code. If
> every test reaches through the GUI and grabs whichever process or struct is
> convenient, the tests eventually freeze the internals in place. Boundary
> lets us say which kinds of observation and control are legitimate—and makes
> the compiler complain when the suite quietly invents a new back door.

The Boundary documentation describes module groups with explicit dependencies
and exports, and supports compile-time enforcement of those relationships:
[`Boundary documentation`](https://boundary.hexdocs.pm/Boundary.html).

### The anti-cheat system can be taught to permit cheating

The honest complication is worth making central to the post: adding Boundary
does not make tests automatically honest. During development, an LLM wanted a
behind-the-scenes capability, encountered the architectural restriction, and
the resulting solution exported that capability through the Boundary. The
mechanism still worked exactly as designed—the declared access became legal—
but the policy itself had been weakened.

Possible phrasing:

> Boundary is an anti-cheat system, but the model is also allowed to edit the
> rulebook. When a test cannot reach an internal module, an LLM may "solve"
> the problem by adding that module to the allowlist. The compiler can tell us
> whether the code obeys the architecture we declared. It cannot tell us
> whether we declared an architecture that lets the test cheat.

Quillex has a concrete example: `BufferSwitcher` is allowed to switch buffers
programmatically because real tab clicks could be lost. That keeps unrelated
scenarios from cascading into nonsense failures, but it may also hide the
very input failure an end-to-end suite is supposed to expose. Likewise, using
the production reducer as a model oracle can prove that the GUI delivery
pipeline matches the reducer, but cannot independently prove that the reducer
itself is correct.

The lesson is not to remove Boundary. It is to treat changes to `exports` and
`deps` like changes to a capability or security policy. Every exception needs
an explicit consumer, proof limitation, and removal condition. This is
especially important in agent-driven development, where making the compiler
green is a powerful local incentive.

## Quiet tests: observability has a token budget

Another practical lesson from developing Quillex with agents is that a test
suite needs an output interface designed for machine collaborators. Spex drives
a real Scenic window and a full run can emit thousands of lines. Streaming all
of that into an LLM conversation is expensive and counterproductive: success
noise consumes context, the relevant failure scrolls out of attention, and the
model spends tokens rereading output that a search tool could locate exactly.

Quillex therefore has two wrapper layers:

- `scripts/run_spex.sh` runs the real GLFW suite and manages the X11 window
  pinner;
- `scripts/run_spex_quiet.sh` redirects the complete run to a timestamped log
  and prints only the exit code, log path, failure headers, result summary, and
  timing.

The agent sees a compact control-plane response:

```text
exit: 1
log:  /tmp/spex_run_....log
--- failures ---
...
--- summary ---
116 tests, 1 failure
```

It can then use targeted searches and bounded reads against the durable log
instead of ingesting the entire transcript. Spex also supports explicit JSONL
failure output, which points toward an even better division:

```text
human/agent live channel  -> short progress + final summary
plain full log            -> searchable chronology and raw diagnostics
structured failure file   -> parseable scenarios, seeds, locations, timings
artifacts                  -> screenshots and semantic snapshots on demand
```

This is more than a cost optimization. It improves reasoning quality. A quiet
runner makes the important facts salient while preserving complete evidence
for later analysis. The system does not discard detail; it changes detail from
an unsolicited stream into a queryable resource.

Possible phrasing:

> Once your collaborator pays for every token it reads, test output becomes an
> API design problem. “Verbose” is not the same as “observable.” The useful
> interface is a small summary linked to complete, searchable, preferably
> structured evidence.

There is also an honest feedback loop here. Agent-generated tests tend to add
logging while debugging; left unchecked, each investigation makes every later
run noisier and more expensive. Quiet-mode execution, structured artifacts,
and cleanup of temporary diagnostics are part of maintaining an agent-friendly
test suite—not optional shell polish.
